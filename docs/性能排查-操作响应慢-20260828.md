# User 端操作响应慢 — 根因排查报告

日期：2026-08-28 ｜ 排查方式：代码走读 + 线上实测 + 副本库基准（`/tmp/survey_perf.db`，**未读写线上 survey.db 任何一笔**）

## 结论（先行）

**后端不是瓶颈**（SQLite 33MB / 2187 行 / 查询全走索引，服务端计算 1~70ms）。
慢在四类问题，按影响排序：

| # | 根因 | 证据 | 影响 |
|---|------|------|------|
| 1 | **打卡点击后 GPS 冷启动最长 10 秒**，期间只有 1.5 秒 toast，之后无任何反馈 | `app.js:2461-2493`：`enableHighAccuracy:true, timeout:10000, maximumAge:0` | 打卡"点了没反应"的直接原因 |
| 2 | **每次切页都全量重拉小班列表（1.3MB）并全量重渲染**，无任何客户端缓存 | `app.js:735/791/1674` 三处 `fetchJSON(.../subcompartments)`；`:511/:589` 一次 `innerHTML` 拼 2187 行 DOM | 搜索小班慢、低端机主线程卡死数秒 → 所有点击无响应 |
| 3 | **静态 JS gzip 静默失败**，app.js 186KB 原样传输 | `app.py:104-106`：静态响应 `direct_passthrough=True`，`get_data()` 抛 RuntimeError 被 `except` 吞掉；线上实测 `Accept-Encoding: gzip` 仍返回 186KB、无 `Content-Encoding` 头 | 弱网首屏慢 |
| 4 | **Leaflet/jspreadsheet 走公网 CDN**（unpkg/jsdelivr），`<script>` 同步阻塞 | `base.html:10-23` | 野外弱网/无外网时页面长时间假死 |

次要因素：

| 问题 | 证据 | 影响 |
|------|------|------|
| 小班详情接口每次都带 `geom_geojson`（平均 8KB、最大 86KB），打卡/样地/调查页都不需要 | `app.py:339-352` 返回整行；`_row_to_dict` 含全部列 | 每次点击多传几十 KB |
| 地图 geojson 接口 10MB（gzip 后 3MB），且服务端每次实时拼接 525ms | 实测 `GET /api/projects/<pid>/geojson` | 地图页弱网 30 秒级 |
| 打卡成功后 `fillSampleCoords` 再串行拉全表调查行 + PUT 回填 | `app.js:2389/2423` | 一次打卡 = 4 步串行网络往返 |
| 全部 `/api/*` 强制 `no-store`（防串号，本身正确） | `app.py:60-68` | HTTP 层缓存全灭，必须靠应用层缓存补 |

## 实测数据（副本库基准 + 线上 curl）

| 接口 | 服务端耗时 | 原始体积 | gzip 后 |
|------|-----------|---------|---------|
| 小班列表（2187 行，无几何） | 72ms | 1299KB | 58KB |
| 小班列表 with_geom=1 | 104ms | 10.6MB | 3.0MB |
| 地图 geojson | 525ms | 10.1MB | 3.0MB |
| 小班详情（平均） | 1ms | 22KB | 7KB |
| 小班详情（最大几何） | 1ms | 87KB | 28KB |
| /api/schema | 1ms | 25KB | 2KB |
| 线上 healthz TTFB（本机网络） | 170~430ms | — | — |

线上验证：`app.js` 带 `Accept-Encoding: gzip` 请求 → 返回 **185985 字节原文**、无 `Content-Encoding` 头（服务器 nginx/1.29.5 本身也未开 gzip）。

## 对两个提议的评估

1. **小班列表缓存到客户端（固定项目+分类）→ 可行，强烈建议做。**
   方案：`localStorage` 按 `pid+project_name+category` 存列表 + 时间戳；进页面先用缓存秒开渲染，后台再拉最新做 stale-while-revalidate；保存/打卡后局部更新缓存。注意换账号登录时清缓存（串号防护，与 `_api_no_store` 的初衷一致）。

2. **API gzip → 已经实现了，但有坑要修。**
   `app.py` 已有 `_gzip_response`（JSON 本地实测生效，25KB→2KB）。要修两处：
   - 静态文件 passthrough bug：在 `get_data()` 前加 `resp.direct_passthrough = False`（或对 send_file 响应先 `resp.direct_passthrough = False`）；
   - 服务器 nginx（1.29.5）当前没开 gzip，建议直接在 nginx 层开 `gzip on`（覆盖静态+API，应用层代码零改动）。

## 修复建议（按性价比排序）

1. **nginx 开 gzip**（服务器一行配置，全站受益，最快见效）。
2. **修 `_gzip_response` 的 passthrough bug**（`app.py:104` 附近加一行）。
3. **小班列表客户端缓存 + 秒开**（见上方案，消掉三处全量重拉）。
4. **打卡体验**：点击即弹 loading 遮罩 + 禁用按钮；GPS 改两段式（先 `maximumAge:30000` 快速返回，后台再精定位）；`fillSampleCoords` 失败不阻塞打卡提示。
5. **列表渲染优化**：搜索结果分页/分块渲染（每次渲染 200 行 + "加载更多"），或虚拟滚动。
6. **CDN 库本地化**：leaflet/jsuites/jspreadsheet 下载进 `static/vendor/`，弱网/离线可用。
7. **详情接口瘦身**：`/api/subcompartments/rows/<id>` 默认剔除 `geom_geojson`（需要时 `?with_geom=1`）。
8. **geojson 接口加服务端缓存**（按 pid 缓存拼装结果，10MB 拼装 525ms→~0ms）。

## 排查过程留档

- 副本库：`/tmp/survey_perf.db`（分析用，可删）；基准脚本：`/tmp/bench_survey.py`。
- 线上只做了 healthz / 静态文件 HEAD 无鉴权探测；未登录任何业务接口、未写任何线上数据。

# 附录：轨迹 15s 上传并发写锁排查与修复（2026-08-28 晚）

## 结论

轨迹 15 秒上传**不会长时间锁库**（WAL 模式写入是毫秒级短锁），但发现并修复了一个真实并发 bug：

| 问题 | 机制 | 后果 |
|------|------|------|
| **跨进程写冲突立即报错** | 生产 `gunicorn -w 2`（2 个进程），`storage._lock` 是进程内 threading.Lock 跨进程无效；SQLite 默认 `busy_timeout=0` | 两进程同时写 → 立即抛 `database is locked` → 轨迹静默保存失败、打卡偶发报错 |
| 全局并发仅 2 | 4 个应用共享 2 个 sync worker（部署说明.md:10） | 一个慢请求（geojson 10MB / 导出 xlsx）占住 worker，全部应用排队 → 点击无反应的另一根因 |

## 已执行修复（最小侵入，一行代码）

`survey/core/storage.py::_connect()`：加 `timeout=5.0` + `PRAGMA busy_timeout=5000`。
写冲突从"立即报错"变为"排队等待 5 秒自动重试"，WAL 下读不阻塞写，5s 余量足够。

**轨迹上传协议保持覆盖式不变**：协议幂等、断网安全（失败下次重传全量）、每人只写自己的小班行。改成增量协议属于高风险改动，收益小，不做。

## 验证

- 新增 `tests/test_concurrent_write.py`：multiprocessing spawn 模拟双 gunicorn worker，2 进程 × 40 组打卡+轨迹高频并发写 → 零次 locked、数据完整；另验证 busy_timeout 配置防回归。
- 全量 112 项测试通过；反向验证（临时 timeout=0）确认旧代码确实复现 locked，测试有效。
